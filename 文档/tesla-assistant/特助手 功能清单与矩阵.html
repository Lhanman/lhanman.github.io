特助手 功能清单与矩阵

围绕特斯拉用车场景，做周边设备互联和车机控制。把车变成一台能被手机、手表、语音和家里设备顺手调用的设备。

20 项功能 候选清单，不排期 优先级待定 20 项均已调研 个人自用 demo 阶段

体验价值

每个功能都问一句：能不能少一步、少一次等待，或者多一点仪式感。下文用这四个标签。

省一步

原本要在车机或官方 App 里点几下，现在一句话或一个按钮搞定。

免等待

上车前就把温度、座椅、导航备好，不用坐进去再等。

仪式感

一个场景名对应一组动作，比如“下班模式”“午休模式”。

安心

离车后门窗、充电状态心里有数，该提醒的会提醒。

整体结构

入口很多，出口只有一个：所有车控都经过指令网关，分级和确认只做一次。

虚线是近场蓝牙，不经过云端，对应 P4。导航分析（N1–N3）只读，不走指令网关，直接使用数据通道里的数据。

调研结论

调研分两轮，都在 2026-10-16 完成。第一轮：20 项功能各由一个子代理查官方资料。第二轮：把所有“无法证实”的项按主题合成 5 组，再各派一个子代理复核，网页抓取读不到时改用浏览器读渲染后的页面，记录在 research/recheck/。标签含义：已复核是我亲自打开官方页核对过；二轮是二轮子代理读到官方原文，我读了报告但没有逐条回到原页核对。 20 项仍然都只到“部分可行”：没有一项到“已确认可行”，也没有一项被判为不可行。二轮的变化是把不少“无法证实”变成了确定的结论（中国区端点、BLE 范围、Telemetry 推送规则、代理的签名与唤醒行为），同时发现了新的风险（个人申请门槛、7 个指令经代理可能 400）。剩下的未知基本都要靠自己的账号和车实测。

1

首次实测：国行车的链路和只读接口已调通

实测
  • 2026-10-18 用自己的国行车实测：developer.tesla.cn 个人身份创建应用通过，lhanman.github.io 被接受为域名，register、授权、GET /api/1/vehicles、GET vehicle_data 都返回 200。国际站应用对国行车无效，返回 client_not_found。
  • access token 有效期实测为 28800 秒（8 小时）。
  • vehicle_data 的 endpoints= 有效值：charge_state、climate_state、drive_state、vehicle_state、location_data；closures_state 无效。分号连接多个分组时只返回了 charge_state，多分组写法待查。
  • REST 键名已证实：门 df/dr/pf/pr/ft/rt、车窗 fd_window 等、locked、sentry_mode、胎压 tpms_pressure_*、media_info 都在 vehicle_state 里；带 location_data 时 drive_state 多出 latitude、longitude、heading。
  • 停放且未导航时，drive_state 里没有 active_route_*；导航中是否出现，要开着导航再测。国内计费、休眠车辆行为、签名指令和 Telemetry 在国行车上的表现仍未验证。记录见 research/live-test-2026-10-18.md。

中国大陆：端点已确认，计费和个人注册仍是未知

二轮
  • 官方原文确认：中国区 API 地址是 https://fleet-api.prd.cn.vn.cloud.tesla.cn；OAuth 用 auth.tesla.cn（token 端点 https://auth.tesla.cn/oauth2/v3/token）。国际站的 token 域名 fleet-auth.prd.vn.cloud.tesla.com 不能用于中国车辆。
  • 调用中国车辆要有 tesla.cn 账号，并在 developer.tesla.cn 另建应用，需要 +86 手机号；每个应用要调用一次 register，域名下要托管公钥（官方中文站原文）。
  • 官方“可付费和修改计费限额”国家名单里没有中国大陆（香港、澳门在名单里）。中国区站点没有计费页，那里的 subscription-plans 是 2024 年的旧内容，不能作依据。中国大陆账号能否开通计费，仍无法证实。
  • 中国区文档没有排除国行车型，也没有任何国行实测说明。Home Assistant 官方集成明确写“暂不支持中国区”；Tessie 文档列出了中国区地址。
  • 更正上一轮：base-urls 页不存在（404），区域信息在 regions-countries 页。developer.tesla.cn 抓取为空是因为前端渲染，用浏览器打开并等约 8 秒就能读到。
  • 中国区文档里虚拟钥匙链接并存 tesla.cn/_ak/… 和 tesla.com/_ak/… 两种写法，以哪个为准要真机验证。

个人自用的门槛：官方要求“合法商业详细信息”

二轮
  • 官方创建应用的页面写：需提供 legal business details、应用名称、描述和使用目的。个人能否申请，官方没有明文，国际站和中国站都没有。
  • 另一方面，官方 Third-party token 的说明里写了面向“hobbyists building an integration with their own Tesla product”，计费页也写每月 $10 折扣用于支持个人开发者和小应用。两处没有矛盾，但个人注册能否通过必须实际申请一次。
  • refresh token 一次性使用、3 个月过期；最近一次用过的 refresh token 24 小时内仍有效；要拿到 refresh token 必须请求 offline_access。access token 有效期官方没写（社区说约 8 小时，不作依据）。
  • scope 清单已由官方 authentication/overview 页确认：vehicle_device_data、vehicle_location、vehicle_cmds、vehicle_charging_cmds 等。上一轮引用的 /authentication/oauth 页是 404。
  • 认证类请求不超过 20 次/秒。client_secret 如何保管，官方没有专门建议，只说私钥要用云 KMS 或 HSM 保管。

vehicle_data：页面位置和字段名要更正

二轮
  • 官方没有独立的 vehicle-data 页，它是 endpoints/vehicle-endpoints#vehicle-data 里的一节。官方只写了“对车辆做实时调用，不建议定期轮询，会很贵”，没有 endpoints 分组名，也没有响应字段表。
  • 官方车端 proto（vehicle.proto）里有：active_route_destination、active_route_minutes_to_arrival、active_route_miles_to_arrival、active_route_traffic_minutes_delay、active_route_energy_at_arrival，以及 charging_state、charge_limit_soc、battery_level、charge_current_request。
  • proto 里没有 active_route_latitude/longitude（只有 active_route_coordinates），也没有 drive_state 下的经纬度（位置在 location_state）。门窗在 proto 里叫 door_open_driver_front、window_open_driver_front 等，没有 df/dr/fd_window 这类缩写。
  • 注意：proto 是车端数据模型，REST 返回的 JSON 键名是否与它一致，官方没写。第三方资料用的是 active_route_latitude 这类 REST 键名，所以“proto 里没有”不等于“REST 里没有”，要拿真实响应对照。
  • 休眠车辆：官方只说是实时调用、车辆不在线返回 408；自动唤醒还是返回缓存，官方没写，官方 Go SDK 的注释又写“离线时可返回缓存”，两者不一致，要真车测。
  • 2023.38 及以上车辆要加 location_data 参数才返回位置；位置、目的地、路线类字段需要 vehicle_location scope，被分享用户（hide_private）会收到 403。读取类请求不需要签名，有官方 README 和代理源码佐证。
5

计费与限流

已复核
  • 按量计费，状态码低于 500 的请求都计费。单价：Data 500 次/$1，Commands 1,000 次/$1，Wakes 50 次/$1，Streaming 150,000 信号/$1；每账号每月 $10 折扣。
  • 官方案例：Telemetry 约每车每小时 $0.00667（约 1000 个信号），同样数据靠 vehicle_data 轮询约 $0.12。每分钟轮询一次约 $86/月，$10 折扣只够平均每天约 160 次。
  • 限流（每设备每账号，同账号多个应用共享）：Realtime Data 60 次/分钟，Wakes 3 次/分钟，Device Commands 30 次/分钟。
  • 计费限额默认为 0；超限后 API 暂停，Telemetry 配置被删除且不会恢复。限额为 0 时调用返回什么状态码，官方没写。
  • vehicle_data 归哪一类计费，官方页没点名，案例里把它算作 Device Data，属推断。各接口的 Pricing Category 在页面折叠区里，抓取读不到。
6

Fleet Telemetry 的行为

二轮
  • 推送规则是“值发生变化，并且距上次发送已过 interval_seconds”才发；车端每 500 毫秒收集一次。不是固定频率，也不是纯变化推送。官方示例里 Locked、DoorState、DetailedChargeState 间隔 1 秒，位置 10 秒，电量 60 秒；MinutesToArrival、RouteLine 没有推荐间隔。
  • 固件要求 2024.26 及以上（直接调用配置接口需 2023.20 及以上）。每辆车同时向第三方推送的接收端数，官方概览页写 5 个，GET 配置接口的说明写 3 个，官方自相矛盾。
  • minimum_delta 的官方说法有两处：公告称只支持数值字段，更新日志称位置字段按米计。prefer_typed 选项已被官方删除；resend_interval_seconds 可让未变化的值定时重发。
  • 配置会在三种情况下被移除：用户撤销授权、所需 scope 被撤销、计费超限。车辆断线时缓冲 5000 条数据。休眠时是否推送、Telemetry 是否让车保持清醒，官方只写“醒着且联网时发送”，没写其他。
  • MinutesToArrival 无目的地时返回 Invalid；RouteLine 是精度 6 的 base64 折线；DetailedChargeState 要固件 2024.38 及以上。接收端要求终结 mTLS（官方 GitHub README）。
7

签名与代理：官方源码里有 7 个指令代理不处理

二轮
  • 官方指令页只明确 set_pin_to_drive、reset_pin_to_drive_pin、set_vehicle_name 必须用 Vehicle Command Protocol；通用规则是“未签名的指令会被车辆拒绝”。完整清单官方没给，保守做法仍是全部经签名代理发。
  • 官方 vehicle-command 源码（main 分支）显示：代理只对 /api/1/vehicles/{vin}/command/{指令} 的 POST 签名，其他路径原样透传；navigation_request 和三个 set_managed_* 指令走 REST 透传。
  • 官方指令页的 72 个指令里，有 7 个在代理源码里没有处理分支，会返回 HTTP 400：navigation_gps_request、navigation_sc_request、navigation_waypoints_request、sun_roof_control、remote_steering_wheel_heat_level_request、remote_auto_steering_wheel_heat_climate_request、upcoming_calendar_entries。这是对源码的推断，线上版本可能不同，需要实测。
  • 对功能的影响：C4 先用 navigation_request；C7 的天窗指令可能不能经代理发。
8

唤醒与指令参数

二轮
  • 代理和 tesla-control 对普通指令都不会自动唤醒车辆；车辆离线时代理返回 408。只有 wake_up 会唤醒（代理会轮询到车辆在线）。官方最佳实践也要求付费请求前先查状态。所以网关要自己实现“查状态、必要时唤醒、再发指令”，并遵守每分钟 3 次的唤醒限流。
  • 官方指令页写明的前置条件：flash_lights、honk_horn 须驻车；charge_port_door_open 在非 P 档时失败；座椅和方向盘加热需预热或保温已开；adjust_volume 需用户在车内且开启移动端访问。
  • 官方页给出的参数不多：actuate_trunk 的 which_trunk，set_climate_keeper_mode 取值 0–3，sun_roof_control 取 stop/close/vent，remote_boombox 取 0 或 2000，限速和家长控制限速为英里/小时。
  • 其余参数名来自代理源码，不是官方文档：set_temps 读 driver_temp、passenger_temp；set_charge_limit 读 percent；set_charging_amps 读 charging_amps；set_climate_keeper_mode 读 climate_keeper_mode；add_precondition_schedule 读 lat、lon、precondition_time、one_time、id、enabled。
  • 官方页说关窗要带 lat、lon，代理源码的 window_control 只读 command，两者不一致，以实测为准。navigation_gps_request 的坐标系官方没写（Home Assistant 只写“度”），国内车要实测是否有偏移。
9

蓝牙（P4）：能做的比上一轮判断的多

二轮
  • tesla-control 的命令表（官方源码）里，除 rename-key、get、post、product-info 需要 Fleet API 外，其余大多数指令都能走 BLE：锁车解锁、空调、鸣笛闪灯、充电、媒体、前后备箱、车窗、座椅和方向盘加热、访客模式等。没有导航和天窗指令。
  • state <类别>（充电、空调、行驶、位置、车身等）可经 BLE 读取，需要私钥；body-controller-state 在车机休眠时也能经 BLE 读，不需要私钥。
  • 距离、延迟、iOS 上的官方实现，官方都没写；国行车是否可用没有说明。
10

周边互联：快捷指令、Home Assistant、推送、免费开发者账号

二轮
  • “获取 URL 内容”支持 GET/POST/PUT/PATCH/DELETE 和请求体，但官方明写不支持 OAuth 2，所以要由自建网关持有 Tesla 凭据，快捷指令只带自己的固定凭据。
  • 个人自动化里有“CarPlay 车载”（连接、断开连接）触发器，关掉“运行前询问”后可直接运行；“通勤之前”不能直接运行。手表只显示在 iPhone 上开启了“在 Apple Watch 上显示”的快捷指令。锁屏、后台运行、手表是否本地执行，官方没写。
  • 大陆：Apple 智能相关的快捷指令动作在大陆不提供；基础动作官方未标注限制。
  • Home Assistant：tesla_fleet 集成明确不支持中国区，也没有预热服务，只有只读的 Preconditioning 传感器、Climate 实体、Wake 和 HomeLink 按钮；rest_command 官方支持自定义 headers。Apple Home 官方手册里自动化的动作只有“场景与配件”，没有发 HTTP；“家庭自动化”要 HomePod、Apple TV 或 iPad 作家居中枢。米家接入 Home Assistant 需米家 App、小米账号，服务器区域选 cn。
  • 推送：Bark 基于 APNs，支持自建服务器；Server酱 免费版每天 5 条；企业微信群机器人每分钟 20 条、文本最长 2048 字节。三者的官方文档都没说境外服务器能否稳定调用，Apple Watch 默认镜像 iPhone 的通知设置。
  • 免费 Apple 开发者账号：App Groups 可用（iOS 和 watchOS），Push notifications 不可用，所以自研 App 收不到远程推送；描述文件 7 天过期，最多 3 台设备、10 个 App ID。

待确认

  1. 国内计费：看开发者后台的账单和用量页，确认国行账号能否绑付款方式、设计费限额，以及实测调用有没有被计费。
  2. 开着导航再调一次 vehicle_data?endpoints=drive_state;location_data，确认 active_route_* 是否出现（N1 的关键）。
  3. 多分组写法：分号连接只返回了 charge_state，试其他分隔写法，或逐组请求。
  4. 车辆休眠时调用 vehicle_data 的行为（唤醒、408 还是缓存），待车休眠后实测。
  5. 添加虚拟钥匙，试一条可逆的车控指令；同时实测官方源码里无处理分支的 7 个指令经代理是否返回 400。

  7. P3 用哪个家居平台，目前未选。P4 的 BLE 在自己的车上支持哪些指令。
