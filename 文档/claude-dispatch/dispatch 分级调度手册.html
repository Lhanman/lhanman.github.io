先判断任务有多复杂，再决定走多重的流程。小事直接做；大事才请出需求拷问、规格文档、子 agent 和终审。目标是在 Pro 订阅的额度里，把 token 花在真正需要的地方。

方案

一套规则，五层分工

同一套重流程用在所有任务上，小改动也要付出拷问、规格和审查的成本；一律轻装上阵，大改动又容易返工。dispatch 在动手前先定级，让流程的重量和任务的风险相称。

规则层ROUTER.md · KB.md会话开始时注入：怎么定级、每级怎么做、何时查和写知识库
编排层主会话定级、执行、判断要不要派子 agent，所有决策留在这里
委派层scout · reviewer · builder只做两件事：替主会话省上下文，或给出独立判断
确定性层hooks · dispatch-verify · dispatch-kb · dispatch-pages本地脚本完成，不调用模型、不耗额度
沉淀层知识库 · 文档站 · OpenSpec 归档 · overrides.log把方案、决策、踩坑、HTML 文档和定级偏差留下来，下次复用

插件本身不含任何项目事实。验证命令和知识库目录由 /dispatch:setup 写进各项目的 CLAUDE.md，个人路径放在本机的 ~/.claude/dispatch/config。同一个插件可以原样用在任何项目、任何机器上。

核心原理

七条原则

每一条都对应插件里的一个具体机制。

  1. 按风险最高的那个信号定级，不取平均改 2 个文件但动了公共接口，按公共接口算。流程是为最坏情况准备的。ROUTER.md · 定级
  2. 主会话是消耗大头，子 agent 要算账约九成消耗在主会话。子 agent 只在两种情况下派：替主会话读大量文件，或需要一个不受主会话思路影响的审查。ROUTER.md · 子 agent
  3. 能用脚本的地方不用模型验证不派 agent，改用脚本跑命令；知识库检索不派 agent，改用脚本出摘要；级别标记由 hook 识别。dispatch-verify · dispatch-kb · hooks
  4. 上下文是最稀缺的资源构建日志落盘，只回摘要；知识库逐层打开；子 agent 回报限 30–40 行；任务组之间 /clear。输出上限 · 上下文卫生
  5. 判断留在主会话，重复劳动交出去需要权衡的实现留在主会话；规格已经写清的机械性任务组才交给 builder。dispatch:builder
  6. 人在关键节点把关L3 以上先征得同意；规格经你审阅才执行；写进知识库的内容先给你看。征得同意 · 规格审阅 · 写入确认
  7. 定级可以纠正，也可以校准写 #L2 就能指定级别，它是下限，要升级会先问你；每次指定和升级确认都记一行日志，积累下来就是修改定级规则的依据。prompt-submit.sh · overrides.log
运行过程

一条需求经过什么

绿色标签的环节由本地脚本完成，不调用模型。

  1. 会话开始
    注入规则

    SessionStart hook 输出 ROUTER.md；配置了知识库时追加 KB.md。新会话、/clear、/compact 之后都会重新注入。

    本地脚本
  2. 每条消息
    识别手动级别

    UserPromptSubmit hook 查找 #L0–#L4。找到就告诉模型按该级别执行，并往 overrides.log 记一行；找不到就什么也不输出。你指定的级别是下限：执行中出现升级信号时先停下问你，你回复 #L3 这样的标记确认后才升级。

    本地脚本
  3. 动手前
    定级

    主会话按风险最高的信号判定级别，回复第一行写 〔L2 · 依据〕。L0 和问答、调研类请求不写。

    主会话
  4. L2 以上
    查知识库

    dispatch-kb search 每篇笔记只回一行摘要，挑中后再看大纲、读小节。

    本地脚本
  5. 执行
    按级别走流程

    按下一节的流程执行，需要时派子 agent。执行中随时重判，升级或降级时说明原因。

    主会话 + 按需子 agent
  6. 收尾
    验证

    dispatch-verify <命令>：完整日志写进临时文件，只回显退出码、报错行和末尾几行。没通过不得声称完成。

    本地脚本
  7. 值得留下时
    沉淀

    L3 归档后，或 L2 得出值得保留的结论时，提议用 /dispatch:note 写笔记，你确认后才写入。

    主会话
  8. 生成 HTML 后
    发布到文档站

    发布 Artifact 页面后，hook 给出现成的发布命令；dispatch-pages 做敏感检查、补全页面、更新目录页并推送。

    本地脚本
五个级别

定级与流程

执行中改动文件数超过预估的 2 倍、出现架构决策、同一问题修了 2 轮没好、碰到公共接口或迁移，都会升级。问不出未决问题、只需改 1 个文件时降级。升级时，已写的意图和问答结论带到下一级，不重做。你用 #L 指定的级别是下限：不会降到它以下，升级要你确认。

L0直做

一句话说得清的改动：错字、配置值、重命名。

直接改 → 最小验证

直接执行 · 无判定行
L1快修

位置明确的 bug 或小功能，不超过 3 个文件，不碰公共接口。

三行意图（目标 / 不做什么 / 验收）→ 修 bug 先写复现测试 → 改 → 验证。原因不明时转 systematic-debugging。

判定后直接执行
L2标准

跨模块、需求有歧义、新依赖，或碰到公共接口、数据模型、并发、删除。

查知识库 → 范围不清派 scout → grilling 最多一轮 → Plan 模式出方案 → 测试先行实现 → 碰到高风险项时派 reviewer。

判定后直接执行
L3特性

一个会话做不完；改公共接口、持久化格式或做数据迁移；新增一块完整能力。

grill-me → OpenSpec 提案 → 你审规格 → 按任务组执行（组间 /clear）→ reviewer 终审（Opus）→ 核对规格 → 归档 → 沉淀笔记。没有 OpenSpec 时，方案写到 docs/plans/。

先征得你同意
L4史诗

新子系统或大改造，要先做架构决策。

/opsx:explore 定决策 → 拆成多个 L3 逐个走。只有真正独立的部分才并行，最多 3 路，用 git worktree 隔离。

模型与消耗

谁用什么模型

插件的 agent 在各自文件里写死了模型，不随主会话变贵。主会话的模型和强度由你自己设置，插件不改。

角色模型什么时候用边界
主会话你的设置（当前 Opus 5 xhigh）所有任务负责定级和所有需要判断的决策
scoutHaiku 4.5要读 5 个以上文件，或进入不熟悉的区域只读，不加载 CLAUDE.md，最多 12 轮，回报 ≤ 40 行
reviewerSonnet 5；L3 终审指定 Opus 5L2 碰到高风险项；L3 交付前一次只看改动差异，只报正确性问题和遗漏的需求，≤ 40 行
builderSonnet 5规格明确的机械性任务组、L4 并行分支遇到歧义就停下回报，≤ 30 行
验证不用模型每次声称完成之前dispatch-verify 脚本

各种配置的相对消耗

Fable 5.1 xhigh，子 agent 全继承100%
Opus 5 xhigh + 本插件编制（当前）≈28%
Opus 5 medium + 本插件编制≈23%
Sonnet 5 + 本插件编制≈12%

按一个月 60 个 L1、25 个 L2、6 个 L3 估算，用 API 价格作权重，只用于比较高低。Pro 额度按模型怎么折算官方没有公布，实际以 /usage 为准。当前配置里约九成消耗在主会话，额度紧张时先调主会话的模型或 /effort。

知识库

查的时候逐层打开，写的时候先确认

直接读写 Markdown 文件，不需要 Obsidian 在运行，也不经过 MCP。没有配置知识库时，这部分规则不注入会话。

查：三步，每一步只多读一点

第 1 步 · 找dispatch-kb search 词… -d 目录按关键词匹配路径、标题、摘要和正文；同一概念的几种说法用 | 连接，多个版本只显示最新的每篇 1 行，实测平均约 3 行
第 2 步 · 看结构dispatch-kb outline 路径摘要、tags 和带行号的标题大纲一篇约 10–30 行
第 3 步 · 读一节Read offset / limit按大纲的行号，只读需要的那一节只读一节

在一个 45 篇笔记的库上用 12 个查询实测：补上同义词（例如 报错|故障|异常）后，11 个第一条就是要找的，平均每次只输出约 3 行。不整篇通读，也不对整个知识库 Grep。L0、L1 不查。

写：固定格式，便于检索

/dispatch:note 先查重（已有同主题的笔记就问你是更新还是新建），再按下面的格式起草，把路径、摘要、tags 和结论给你看，你确认后才写入项目对应的目录。

文档站

生成的 HTML，自动汇成一个文档站

每次生成或更新 HTML 文档（包括 Artifact 页面），都同步发布到 lhanman.github.io。目录页按发布记录自动生成，可以搜索、按标签筛选。

触发PostToolUse · ArtifactArtifact 页面发布后，hook 给出带文件路径和 slug 的发布命令；已发布过的页面按更新处理没配置文档站时不输出
把关dispatch-pages publish先查本机路径、邮箱、密钥、敏感词和 Artifact 专属能力，命中就停下给你看退出码 3，未发布
上线/p/<slug>/仓库里按项目分目录、用中文标题存放（文档/<项目>/<标题>.html），推送后由 GitHub Actions 部署成英文网址约 1 分钟后生效

站点是公开的。GitHub Pages 即使用私有仓库发布，页面也谁都能打开，所以工作项目的内部内容不发布。拦截哪些词写在 ~/.claude/dispatch/config 的 pages_deny 里，随时可以增删；确认无妨的内容，可以用 --allow 放行。

如何使用

第一次使用

  1. 新开一个会话规则在会话开始时才注入。提一个开发需求，回复第一行出现 〔L2 · 依据〕 这样的判定，就说明生效了。
  2. 在项目里执行 /dispatch:setup探测构建方式，拟出 L0 到 L3 以上各级的验证命令让你确认；检查 git 和 OpenSpec；确定这个项目在知识库里对应哪个目录。结果写进项目的 CLAUDE.md。每个项目做一次。
  3. 照常提需求不需要记任何命令，级别自动判定。想指定级别，就在消息里任意位置写 #L0–#L4。
  4. 用上 1–2 周后复盘看 ~/.claude/dispatch/overrides.log，你手动改级别的次数和方向就是定级规则需要改的地方；再用 /usage 对比额度消耗。

问题与限制

常见问题

回复里没有判定行？
规则只在新会话、/clear、/compact 之后注入，已经开着的会话不会生效。另外，L0 和问答、调研类请求本来就不写判定行。
定级偏高或偏低？
当下用 #L 纠正。积累 1–2 周后，看 overrides.log 里偏差集中在哪一级、哪类任务，再改 router/ROUTER.md 的定级信号。
想脑暴？
直接说「脑暴一下……」，或执行 /dispatch:brainstorm。结论要落地就转入对应级别的流程；要留存就写成知识库笔记，或整理成 HTML 发到文档站。
额度还是不够用？
先降主会话：换 Sonnet 5，或把 /effort 调低；做 L3 规划时可以临时切到 /model opusplan（规划用 Opus，执行用 Sonnet）。再在 settings.json 的 env 里加 "CLAUDE_CODE_SUBAGENT_MODEL": "sonnet"，内置的 Explore、Plan agent 就不会继承主会话的贵模型。
项目没有 OpenSpec？
L3 会把方案写到 docs/plans/。需要时在项目里执行 openspec init --tools claude。
知识库没生效？
执行 dispatch-kb path，检查 ~/.claude/dispatch/config 里的 kb_dir。这部分功能还需要本机有 python3。

已知限制

  • 常驻开销约 2.3k token/会话：路由规则约 1.2k，知识库规则约 250，文档站规则约 100，其余约 800 是各 skill 和 agent 的描述。
  • 文档站是公开的，是否发布只靠敏感检查判断；敏感词列表要你自己维护。
  • 消耗对比是用 API 价格估算的相对值；Pro 额度的实际折算方式未公开。
  • 定级由模型判断，会有偏差；目前靠 #L 纠正和手动复盘，还没有自动复盘。
  • 知识库里的旧笔记没有 frontmatter，检索时摘要取的是正文第一段，可能不准。
  • 插件里的 agent 不支持 hooks、mcpServers、permissionMode 这几个字段，这是 Claude Code 对插件 agent 的限制。
  • 插件仓库只执行过 git init，还没有提交。
  • Artifact 发布后的提醒 hook 已用模拟输入测过，还没在真实会话里触发过。
