分级调度方案

先判断任务有多复杂，再决定走多重的流程：小事直接做，大事才请出提问、规格文档和子 agent。方案与技术栈无关，已经做成全局插件，所有会话都生效。这一版按 Pro 订阅重新设计了模型分配，目标是少耗 token。

方案核心

五级分流

级别按风险最高的那个信号来定，不按平均值：只要碰到公共接口或数据模型，至少就是 L2。问答、调研、写文档这类非开发请求不定级，也不写判定行。

机制

路由、升级与降级

  1. 会话开始时：SessionStart hook 把路由规则（router/ROUTER.md，37 行）注入上下文。/clear 和压缩之后会重新注入。
  2. 判定：L1 起，回复第一行写判定结果和依据，例如：
    〔L2 · 新增依赖 + 跨两个模块〕
  3. 手动指定：在消息里写 #L0–#L4，UserPromptSubmit hook 识别后按你指定的级别走。没有标记时 hook 不输出任何内容，不占上下文。两个 hook 都是本地脚本，不调用模型。
  4. 征求同意：L0–L2 判定后直接执行；L3 以上先得到你的确认。
  5. 执行中重新判断：出现下面任意一个信号，就调整级别，并说明原因。

↑ 升级信号

  • 实际改动的文件数超过预估的 2 倍
  • 出现架构决策
  • 同一个问题修了 2 轮还没好：先转系统化调试，仍不行就清空上下文重写提示
  • 碰到公共接口、序列化格式或数据迁移
  • 一个会话做不完

升级时，已经写好的三行意图和问答结论带入下一级，不重做。

↓ 降级信号

  • 提问问不出新的未决问题
  • 拆出来的任务不到 3 项
  • 摸清现状后发现只需要改 1 个文件

每次手动指定级别，hook 都会在 ~/.claude/dispatch/overrides.log 记一行（时间、级别、目录）。它反映自动判定哪里不准，是以后修订规则的依据。

编制

子 agent 与模型

原则：只有在能节省主会话上下文、或需要独立判断时，才派子 agent。每个 agent 的定义里都规定了回传格式和长度上限（30–40 行）。

主会话 由你设置 · 你选的是 Opus 5 xhigh

负责判定级别、规划、需要判断的实现和最终把关。它占总消耗的大头，是调整消耗最有效的地方。

dispatch:scout Haiku 4.5 · 只读 · 最多 12 轮

要读 5 个以上文件或进入不熟悉的区域时用。不加载 CLAUDE.md，启动开销小。只回传结论和"文件:行号"列表。

dispatch:reviewer Sonnet 5 · 只读 · L3 终审指定 Opus 5

全新上下文，只看改动差异，只报正确性问题和遗漏的需求。没发现问题就直接说通过。

dispatch:builder Sonnet 5 · 可编辑

只接规格明确的机械性任务组，或 L4 的并行分支。遇到歧义或越界就停下来回报，不自行决定。

和 v0.1 相比：验证不再用子 agent，改成脚本（见"验证"一节）；reviewer 从"L2 以上每次都过"改成按风险触发；builder 从 L3 默认使用改成只接机械性任务。

Claude Code 内置的 Explore、Plan 等 agent 默认继承主模型。主会话用 Opus 时，建议在设置的 env 里加 CLAUDE_CODE_SUBAGENT_MODEL=sonnet 兜底；本插件的 agent 在各自文件里写明了模型，优先级更高，不受影响。

验证

一个脚本，加上每个项目自己的验证矩阵

dispatch-verify <命令> 执行验证命令，把完整日志写入临时文件，只回显退出码、报错行和末尾几行：通过时 8 行，失败时 40 行。构建和测试的长输出不进入上下文，这一步也不消耗模型额度。插件启用期间，这个命令自动在 PATH 里。

用哪些命令验证，每个项目不一样，所以不放在插件里。在项目里执行 /dispatch:setup，它会探测构建方式，拟出下面这张表，给你确认后写进项目的 CLAUDE.md：

级别目的
L0最快的检查：只编译或只做类型检查改动所在的部分
L1受影响部分的单元测试 + 编译
L2全部测试 + 静态检查
L3 以上完整构建，包含打包、链接等发布前步骤

setup 还会检查两件事：项目是不是 git 仓库（不是的话，reviewer 拿不到改动差异，L4 用不了 worktree；它只建议初始化，不会替你执行）；OpenSpec 是否就绪（没有的话，L3 退回到把方案写进 docs/plans/）。不执行 setup 也能用，路由规则会从构建文件推断验证命令。

接下来

先用起来，再根据记录修订

方案是拼出来的，还没有经过真实任务验证。常见的风险是规则执行走样：级别判错，或者该升级时没升级。建议用 1–2 周、积累约 20 个任务后看三件事：

  • overrides.log 里你手动改级别的次数和方向：总是往上改，说明判定偏轻；总是往下改，说明偏重。
  • 用 /usage 对比任务前后的额度变化，校准上面的消耗估算。
  • 哪一级用起来别扭，哪个子 agent 几乎没被派出过。

留到以后的：一个手动命令，读取覆盖记录并给出规则修订建议；用 claude plugin eval 做一组"提示 → 期望级别"的回归测试。两者都要等有了真实数据再做。

附录 · 调研结论

业界共识：八条原则

这些原则来自 Anthropic 的工程博客、Claude Code 官方文档，以及 superpowers、BMAD、Kiro 等框架的实践和社区反馈。

  1. 先从简单做起，有明确收益再加复杂度。 能用固定流程解决的，就不要上 agent；能一个 agent 做完的，就不要拆成多个。 Anthropic · Building Effective Agents
  2. "一句话能说清改动，就跳过规划。" 这是官方给出的最清晰的分级线。方案不确定、要改多个文件、代码不熟悉时，才需要先规划。 Claude Code Best Practices
  3. 把工作量预算写进提示词。 Anthropic 的研究系统把规则写死在提示词里：简单任务 1 个 agent、3–10 次工具调用；对比类 2–4 个子 agent；复杂任务 10 个以上。不写的话，模型会在简单问题上过度投入。 Multi-agent Research System
  4. 多 agent 很贵，而且大多数编码任务并行不起来。 单 agent 的 token 消耗约为普通对话的 4 倍，多 agent 约为 15 倍。官方原话是"大多数编码任务"不适合多 agent，因为可并行的部分有限。子 agent 最大的价值是隔离上下文，不是提速。 同上
  5. 强模型编排，便宜模型干活。 Opus 做主导、Sonnet 做子 agent，比单独用 Opus 在内部评测上高 90%。Aider 把"想方案"和"改代码"分给两个模型，Claude Code 的 opusplan 模式也是同样的思路。但是轮数比单价更重要：需要判断的任务交给小模型，反复试错的轮次多了，总成本反而更高。 Anthropic · Aider · superpowers
  6. 只保留一个路由器。 superpowers 的规则是"哪怕只有 1% 可能适用也要调用技能"，结果被普遍批评为小任务过度设计。社区还明确警告：两套路由规则同时运行会互相打架。 superpowers #1501 · dev.to 三派对比
  7. 流程要能升级，也要能降级。 BMAD 在执行中发现任务比预想的大时会自动升级，并且已经写好的文档继续复用。反过来，发现任务很小就退回简单流程：这一点所有框架都没做到，是本方案要补上的。 BMAD v6 · 本方案
  8. 结果要验证，不能只信 AI 说"做完了"。 每个非简单任务都要有能跑的检查。审查交给一个全新上下文的 reviewer，并且只让它指出正确性问题和遗漏的需求，否则它会推着你过度设计。 Claude Code Best Practices

另外两条常用的上下文管理原则：无关任务之间用 /clear；同一个问题纠正两次还没好，就清空上下文重写提示词。CLAUDE.md 控制在 200 行以内。

附录 · 调研结论

按你的场景，谁最好

这些框架都没有公开可比的评测，唯一有硬数据的是 Anthropic 的研究，而它讲的是通用原则，不是某个具体框架。所以下面的排名是按你的场景给的：个人开发、Claude Code、Pro 订阅。

排名方案理由
1Pocock skills + OpenSpec最轻、可以自由组合，和你已经装好的东西完全一致。缺点是没有自动判断复杂度，要靠你自己决定用哪个
2superpowers纪律最强：强制写测试、每个任务单独开子 agent 并审查两遍、完成前必须验证。缺点是所有任务都走全套流程，没有快速通道，小任务明显过度设计
3BMAD v6分级思想最成熟，执行中发现任务变大会自动升级。缺点是要先拆完需求才能定档，仪式感重，更适合团队
4oh-my-openagent按任务类别配模型的设计最好，但它属于 OpenCode 生态，搬到 Claude Code 要自己重写
—spec-kit / Kirospec-kit 流程太重；Kiro 要绑定它自己的 IDE。都不适合你

各单项做得最好的

流程纪律superpowers
分级与自动升级BMAD
按任务配模型oh-my-openagent
轻量、可组合Matt Pocock
持续维护的需求文档OpenSpec

本方案的定位

以 Pocock + OpenSpec 为底，加上 BMAD 的自动升级、oh-my-openagent 的按类别选模型、superpowers 的审查环节，再补上各家都没有的降级机制。

它是纸面上的最优，还没有经过真实任务验证，验证办法见"接下来"一节。
